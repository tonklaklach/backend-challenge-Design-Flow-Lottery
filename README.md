# backend-challenge-Design-Flow-Lottery

เอกสารออกแบบระบบค้นหาและจองสลากสำหรับข้อ 2 ใช้ข้อมูล **1 ล้านใบ** และเลขสลาก 6 หลัก ตามโจทย์ที่ได้รับ เอกสารชุดนี้ใช้ส่งต่อให้ทีมพัฒนาวางแผนและ implement ได้ โดยยังไม่มี API server หรือผลทดสอบประสิทธิภาพจริง

โจทย์ต้นทาง: [7-solutions/backend-challenge](https://github.com/7-solutions/backend-challenge) จำนวนข้อมูลในเอกสารนี้ยึดโจทย์ 1 ล้านใบที่ใช้ในการออกแบบ

## ระบบนี้ทำอะไร

ผู้ใช้ค้นหาด้วย pattern เช่น `****23` เพื่อหาสลากที่ลงท้ายด้วย `23` เมื่อค้นหาสำเร็จ ระบบจะจองสลากที่คืนให้ผู้ใช้นั้นทันที เป็นเวลา 5 นาทีตามค่าที่เสนอ ระหว่างนี้ผู้ใช้อื่นจะจอง **สลากใบเดียวกัน** ไม่ได้ แม้ใช้ pattern คนละแบบ

เลือก PostgreSQL ให้เป็นผู้ตัดสินว่าสลากใบไหนว่าง โดยค้นหาและบันทึกการจองให้เสร็จใน transaction เดียว ก่อนตอบกลับผู้ใช้ หากการเชื่อมต่อขาดหลังบันทึกสำเร็จ ผู้ใช้ส่งคำขอเดิมซ้ำด้วย `idempotency_key` เดิมเพื่อรับผลการจองเดิมได้

สลากแต่ละใบมี `ticket_id` ของตัวเอง เลข 6 หลักเหมือนกันได้หากเป็นคนละใบ ส่วนการจองแต่ละครั้งมี `reservation_id` สำหรับเปิดดู ยกเลิก หรือยืนยันการจอง

## คำที่ใช้ในเอกสาร

| คำ | ความหมายในระบบนี้ |
| --- | --- |
| Ticket | สลากหนึ่งใบ ระบุด้วย ticket_id ไม่ใช่เลขสลากเพียงอย่างเดียว |
| Reservation / hold | การกันสลากไว้ให้ผู้ใช้ช่วงหนึ่ง ก่อนยกเลิก หมดเวลา หรือยืนยัน |
| Idempotency key | รหัสที่ client สร้างและใช้ซ้ำเมื่อส่งคำขอเดิม เพื่อไม่ให้ระบบจองเพิ่มโดยไม่ตั้งใจ |
| Transaction | กลุ่มคำสั่งฐานข้อมูลที่ต้องสำเร็จพร้อมกัน หรือยกเลิกพร้อมกัน |
| Commit / rollback | ยืนยันการเปลี่ยนแปลง / ยกเลิกการเปลี่ยนแปลงใน transaction |
| Primary | ฐานข้อมูลหลักที่รับการเขียนและตัดสินสิทธิ์การจอง |

## เรื่องที่ต้องตกลงก่อนเริ่มพัฒนา

โจทย์ไม่ได้กำหนด JWT, เวลา hold, จำนวนผลต่อครั้ง หรือขั้นตอน confirm เราจึงเสนอค่าเริ่มต้นไว้ใน A01–A09 ของ requirement ส่วน confirm เป็นตัวเลือกเพิ่มเติม ไม่ใช่ข้อบังคับของโจทย์ และไม่ได้หมายถึงชำระเงินสำเร็จ

ตัวเลข latency, RPO และ RTO เป็นเป้าหมายสำหรับคุยกับทีมและทดสอบต่อ ยังไม่ใช่ผลที่วัดได้จริง
